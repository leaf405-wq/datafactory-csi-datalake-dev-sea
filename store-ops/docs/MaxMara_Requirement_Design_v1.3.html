V1.2 的十个问题，以及 V1.3 的改法

没有匹配的问题。

编号V1.2 的问题落到项目上V1.3 的改法
P-01 三个方案都没有离开 Azure。账本是 Azure SQL，批处理是 Functions 或 ADF，身份是 Entra ID，文件是 Blob。 换前端或后端，订阅、区域和按量账单还在。离开其中一个方案，不等于离开 Azure。 应用可以在 A、B、C 之间选择。数据平面只有一套，部署在客户机房或已有私有云，不调用 Azure 服务。
P-02 租售比和应付租金可能在 Dataverse、Azure SQL、Databricks 或 ClickHouse 里各算一次。 同一家店两个数字。月结对不上时无法判断以哪张表为准。 应付租金只由租金引擎写入 PostgreSQL。租售比、预警等级和 69 列店览只在 dbt 里定义一次，结果放 ClickHouse。
P-03 合同解析指向 Azure AI Document Intelligence，技术问答仍在讨论 Azure OpenAI。 BRD 已说明公有模型会泄密，也会抽错金额。合同离开公司网络。 原件进客户机房的 MinIO。PaddleOCR 加本机 vLLM / Qwen2.5。低置信度字段必须人工确认。在约 30 份真实合同试过之前，不承诺 95%。
P-04 Power Automate 承担审批和计算触发，流的运行历史被当成过程记录。 流历史保存不了合同修订永久、租金参数 5 年、对账 10 年。Premium 另计费。1000 家店不能写进一条流的循环。 审批状态在应用里走完：草稿、审批中、生效、变更。账和审计在 PostgreSQL。已有 M365 时，流只投递文件和调用接口。
P-05 分析库没有选定。T-07 仍是问句，正文同时出现 ClickHouse、Databricks 和 Azure SQL。 店览 69 列没有落点，后续每加一张报表都要重新选工具。 分析库定为 ClickHouse。节奏是 T+1 和月结，不做毫秒级实时。
P-06 历史依赖 SQL Server 时态表。 一旦换数据库，合同变更和关账轨迹要重做。 合同与租金参数用 valid_from、valid_to。审计表只追加，并记录前一条哈希。应用账号不能删除审计行和已关账月份。
P-07 部署区域绑在 Azure 全球或世纪互联，跨境是开放风险，也是费用项。 选区域本身就要单独评估订阅、延迟和数据出境。 默认放在客户机房或客户已经在用的私有云。合同文件不出该环境。是否跨境交给法务，不再默认上公有云。
P-08 识别按页、模型按 token、数仓按仓库时长、数据库按 vCore 计费。 门店和合同一多，账单随用量涨，和功能是否用满无关。 PostgreSQL、ClickHouse、dbt、Airflow、MinIO、Superset、Keycloak、OpenBao、Grafana 无软件许可证费。费用变成机器、磁盘和运维。OCR 可先用 CPU，批量上来再加推理卡。本稿不报单价。
P-09 正文引用 MaxMara_Requirement_media 下的四张架构图，附件里没有这些文件。 打开 V1.2 时架构图是断的。 V1.3 的图都写在页面里，用 mermaid 画出，不再外链缺失的图片。
P-10 验收标准在 PRD 和 BRD 里互相打架，V1.2 把它们同时写进不同组件。 500 店 10 秒和 1000 店 2 小时、4 个模型和 10 个以上模型、租售比 25% 和 30%，会做成两套逻辑。 批处理按 1000 家店、2 小时。一期五个模型。租售比先按 BRD，待财务用近 12 个月数据签字。缺销售标成数据异常，不算业务预警。

改进时守住的六件事

  • 一套数据平面。方案 A、B、C 只换办理界面和审批入口，不换账本。
  • 合同、账单、密钥留在客户环境。抽取模型也留在同一环境。
  • Gold 口径只写在 dbt。应用和报表都读结果，不各自写公式。
  • 租金引擎无界面、先有测试向量，以后可以从 Node.js 迁到 Java，或反向，测试用例跟着走。
  • 关账月份不可覆盖。失败重跑只处理未关账月份。
  • AI 做抽取、检索和文字说明。金额以规则引擎和人工确认为准。

租金顺序

与月结流程图一致，系统轨迹使用同样的步骤名：是否免租，当月模型，固定租金、销售额、扣点，取高或取低，物业、推广、水电，扣补贴，增值税。

  • 免租月份只要与免租区间重叠，整月基础租金为 0，不做半月折算。物业默认仍计，除非合同写明免除。
  • 扣点租金 = 销售额 × 扣点。两者取高取较大值，两者取低取较小值。
  • 增值税默认 9%，税基为 max(0, 基础租金 + 附加 − 补贴)。财务另有口径时改这一处参数。
  • 租售比用不含税净额。建议阈值：大于 25% 红，20% 至 25% 橙，15% 至 20% 黄。保底销售达成低于 80% 红，低于 90% 橙。
  • 一期模型：两者取高、两者取低、纯固定、纯扣点、保底加超额。阶梯和封顶看在营合同占比再定。不按“10 个以上模型”排期。
  • 没有销售数据时标记为数据异常，不发业务红灯。

利弊与成本

三案比较的是办理方式，不是三套数据平台。账、口径、文件、模型和密钥都在同一工具箱。成本差主要来自要不要保留 M365 流程，以及第一期用 Node.js 还是直接用 Java。

边界

方案适合守住的边界主要代价
要长期月结、审计和权限的生产系统 一个 Spring Boot 应用四个模块。1000 店、2 小时用批处理完成。关账不可覆盖。 第一版比 Node.js 慢一些。团队需要 Java。
先把规则跑通，并保留迁到方案 B 的数据 同一 PostgreSQL、同一 dbt、同一 MinIO。Access 不进入此方案。 若长期停留在 Node.js，大型批处理和严格审计要靠同一套库约束，不能靠脚本补。
M365 已经买了，只想少做一个收件箱 不重算、不入 Dataverse、不循环 1000 店。流历史不是审计。 多一个需要维护的边缘。没有 M365 就不要为它新购 Premium。
